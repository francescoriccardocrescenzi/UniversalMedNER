# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

UniversalMedNER fine-tunes MedGemma (`google/medgemma-1.5-4b-it`, an image-text-to-text model used here in text-only mode) for biomedical Named Entity Recognition. The pipeline has two stages: LoRA supervised fine-tuning (SFT) on synthetically-formatted NER data, then LoRA GRPO reinforcement learning on top of the SFT checkpoint, using custom reward functions. Training data comes from `disi-unibo-nlp/Pile-NER-biomed-IOB` (IOB-tagged NER, converted on the fly into instruction/JSON-output format).

A second task (automatic labelling of entities present in text) is planned to land in the same files (`dataset_code.py`, `train_code.py`, `eval_code.py`, `train_pipeline.py`, `test_pipeline.py`, `run_full_pipeline.sh`) alongside this one. To keep the two unambiguous once that happens, every function/class/constant name, CLI flag, and shell variable specific to the current task carries an `ner`/`NER` marker (e.g. `execute_ner_sft`, `--ner_sft_learning_rate`, `NER_SFT_LEARNING_RATE`) — see "Hyperparameter flags" and "Module structure" below for the full naming convention. Truly task-agnostic code (nothing NER-specific, reusable as-is by any task) instead lives in `util_code.py` and stays unprefixed.

## Setup

- A local venv already exists at `.venv` (Python 3.11, managed with `uv`). Activate with `source .venv/bin/activate`, or prefix commands with `.venv/bin/python`.
- Secrets live in a git-ignored `.env` file with `HF_TOKEN` (must belong to an account with MedGemma access) and `WANDB_API_KEY`. Scripts do `set -a; source .env; set +a`.
- `HF_HOME` is set to `data/.cache/huggingface` by the shell pipeline scripts so the HF cache lands inside the (git-ignored) `data/` directory rather than `~/.cache`.

## Running the pipeline

Everything runs from the repo root. Each run is identified by a `--label`, which maps to a `data/<label>/` directory that receives all outputs (metrics, checkpoints, completions) — it holds no input config. Hyperparameters are plain CLI flags (see "Hyperparameter flags" below), not a file; override any of them by passing `--flag=value` overrides to `run_full_pipeline.sh` (each recognized name is explicitly whitelisted there and forwarded individually to whichever steps use it — anything else is a hard error) or directly to the Python entry points.

`src/run_full_pipeline.sh --label=RUN_LABEL [-1] [-2] [-3] [-4] [-5] [--profile=standard|smoke] [--ner_random_seed=42] [--ner_sft_learning_rate=2e-4] [--ner_grpo_beta=0.0] ...` runs the five stages end-to-end, or only the numbered steps passed:
1. Test the baseline (no adapter) model → `data/<label>/baseline_metrics.json`
2. SFT training → checkpoint pushed to HF Hub under `<label>_ner_sft`
3. Test the SFT checkpoint → `data/<label>/sft_metrics.json`
4. GRPO training on top of the SFT checkpoint → checkpoint pushed under `<label>_ner_grpo`
5. Test the GRPO checkpoint → `data/<label>/grpo_metrics.json`

`--profile` (default `standard`) selects between two execution modes:
- `standard` — the behavior described everywhere else in this doc: hyperparameter shell variables default per the "Hyperparameter flags" section below and are overridable with `--flag=value`.
- `smoke` — ignores the `standard` defaults entirely and hardcodes its own fixed, non-overridable configuration in `run_full_pipeline.sh` (tiny `MODEL_REPO` stand-in, small sample counts, batch sizes, LoRA rank, `NER_*_MAX_STEPS`/`NER_*_SAVE_STEPS`/`NER_*_EVAL_STEPS`, `NER_MAX_RAW_SAMPLES`, etc., and `WANDB_MODE=disabled`), so the whole 5-step pipeline runs in a few minutes on an 8GB GPU. **Any flag other than `--label`/`-N` is a hard error under `--profile=smoke`** — it's meant only to verify that new/modified code runs before pushing to the remote VM, always the same way, not to be tuned. Every value it sets is a plain existing (or newly added) hyperparameter flag under the hood — `smoke` is nothing but a fixed, different set of flag values, not a separate code path in the Python entry points. Checkpoints from a smoke run still get pushed to the HF Hub under `<label>_ner_sft`/`<label>_ner_grpo` like any other run, so use a clearly-scoped `--label` (e.g. `smoke`).

Underlying Python entry points (also runnable directly, but every hyperparameter flag is `required=True` with no python-side default — see "Hyperparameter flags" below — so a standalone invocation must pass all of them explicitly; check `--help` for the full flag list):
- `src/train_pipeline.py --save_folder ... --checkpoint_save_folder ... --ner_mode {sft,grpo} [--checkpoint_load_folder ...] [--ner_reward_fn {structured,soft_f1}] --ner_random_seed ... [...all hyperparameter flags...]` — trains and, on completion, uploads the best checkpoint's LoRA adapter to the HF Hub repo `frc00/UniversalMedNER` (default `--checkpoint_repo`) under `path_in_repo=<checkpoint_save_folder>`.
- `src/test_pipeline.py --metrics_path ... --ner_mode {baseline,sft,grpo} [--sft_checkpoint_folder ...] [--grpo_checkpoint_folder ...] [--temperature ...] [--top_p ...] [--verbose] --ner_random_seed ... [...all hyperparameter flags...]` — downloads the relevant adapter(s) from the Hub, evaluates on the `test` split, writes metrics JSON and a `completions.parquet` (prompt/prediction/ground-truth/reward per sample).

Checkpoints are **not** stored locally beyond transient training checkpoints — the SFT/GRPO adapters live on the HF Hub repo `frc00/UniversalMedNER`, keyed by the `--checkpoint_save_folder` / `--checkpoint_load_folder` names (by convention `<label>_ner_sft` / `<label>_ner_grpo`). `test_pipeline.py` and the GRPO stage of `train_pipeline.py` both `snapshot_download` the needed folder from that repo rather than reading local checkpoint dirs.

## Hyperparameter flags

There is no hyperparameter config file and no shared python module for hyperparameters — `src/run_full_pipeline.sh` is the single source of truth for defaults, as plain shell variables at the top of the script, mirroring the last completed full GRPO run (`data/full_grpo/`, finished 2026-07-07). Every hyperparameter is passed from the shell script to the Python entry points as its own individual `--flag value` argument (never bundled into an array, dict, JSON blob, or namespace object), and each Python entry point declares that flag as its own individual `argparse.add_argument(..., required=True)` call with no python-side default — `train_pipeline.py`/`test_pipeline.py` use `args.<flag>` directly everywhere, with no intermediate config object.

Every flag/shell-variable specific to this task (as opposed to pure path/identity plumbing — see below) carries an `ner_`/`NER_` marker, so a second task's equivalent flags can coexist without colliding (`--ner_sft_learning_rate` / `NER_SFT_LEARNING_RATE`, not `--sft_learning_rate` / `SFT_LEARNING_RATE`). The handful of flags that stay unprefixed are the ones about *where things live*, not *what's being trained/tested/evaluated*, and (aside from historical defaults) don't encode "NER" themselves: `--label`, `--model_repo`, `--checkpoint_repo`, `--checkpoint_save_folder`, `--checkpoint_load_folder`, `--save_folder`, `--metrics_path`, `--completions_path`, `--verbose`, `--temperature`, `--top_p`, `--sft_checkpoint_folder`, `--grpo_checkpoint_folder`.

Fields are grouped by stage, matching the old `hyperparam.json`'s sections, just as prefixed CLI flags instead of JSON sections:

- shared (no prefix beyond `ner_`): `--ner_random_seed --ner_validation_size --ner_test_size --ner_max_entities --ner_target_modules --ner_max_negatives --ner_max_raw_samples --ner_dataset_repo` (`train_pipeline.py` only; `test_pipeline.py` only needs `--ner_random_seed --ner_validation_size --ner_test_size --ner_max_entities --ner_max_raw_samples --ner_dataset_repo`, since target-module selection and negative-entity sampling are training-only concepts)
- sft (`train_pipeline.py` only): `--ner_sft_learning_rate --ner_sft_lora_rank --ner_sft_batch_size --ner_sft_gradient_accumulation_steps --ner_sft_num_epochs --ner_sft_max_train_samples --ner_sft_max_validation_samples --ner_sft_save_steps --ner_sft_eval_steps --ner_sft_max_steps`
- grpo (`train_pipeline.py` always; `test_pipeline.py` only needs `--ner_grpo_max_completion_length`): `--ner_grpo_learning_rate --ner_grpo_lora_rank --ner_grpo_batch_size --ner_grpo_gradient_accumulation_steps --ner_grpo_num_generations --ner_grpo_max_completion_length --ner_grpo_num_epochs --ner_grpo_max_train_samples --ner_grpo_max_validation_samples --ner_grpo_beta --ner_grpo_temperature --ner_grpo_eval_steps --ner_grpo_max_steps`
- test (`test_pipeline.py` only): `--ner_test_batch_size --ner_max_test_samples`

The `ner_sft_`/`ner_grpo_`/`ner_test_` prefixes exist because fields like `learning_rate`, `lora_rank`, and `batch_size` need independently-overridable defaults per stage — a single flag can't carry two different defaults at once. `test_pipeline.py` always uses `--ner_grpo_max_completion_length` regardless of `--ner_mode`, so generation length (and therefore truncation behavior) is comparable across baseline/SFT/GRPO testing. `train_pipeline.py` always requires the full sft+grpo flag surface regardless of `--ner_mode`, since argparse validates required flags before `--ner_mode` is inspected.

`--ner_*_max_train_samples`, `--ner_*_max_validation_samples`, `--ner_max_test_samples`, `--ner_max_negatives`, and `--ner_max_raw_samples` are the only hyperparameters without `required=True` (they default to plain `int` `-1`, meaning "no limit"/"unset"; `0` is a real, distinct value for all of them, e.g. `--ner_max_negatives=0` forces zero negative entities) — `run_full_pipeline.sh` passes these unconditionally like every other flag, no different from any required flag, since `-1` is a valid `int` on its own. There is no shared conversion layer: every function that actually consumes one of these values checks for `-1` directly at the point of use (`dataset_code.format_ner_sft`/`create_ner_sft_ds`/`create_ner_grpo_ds`'s `max_negatives`, `eval_code.evaluate_ner_dataset`'s `max_samples`, `train_code.execute_ner_sft`/`execute_ner_grpo`'s `max_train_samples`/`max_validation_samples`, and the raw-dataset truncation inline in both entry points) — values flow from CLI flag to consuming function unmodified. `--ner_max_raw_samples`, unlike the others, truncates the *raw* dataset immediately after `datasets.load_dataset`, before any formatting/splitting — the other `max_*_samples` flags truncate post-formatting splits, by which point the full dataset has already been mapped over (including the entity-frequency pass in `dataset_code.get_ner_entity_array_and_weights`).

`--ner_sft_save_steps`/`--ner_sft_eval_steps`/`--ner_grpo_eval_steps` (checkpoint/eval cadence, in steps) and `--ner_sft_max_steps`/`--ner_grpo_max_steps` (hard cap on optimizer steps, `-1` = unused/disabled, TRL's own default, overrides `--ner_*_num_epochs` once reached) are `required=True` like the other core hyperparameters. They matter together: `load_best_model_at_end=True` needs at least one eval+save to have actually happened, so a run using few enough samples/steps that the default cadence (200/200/50) never fires needs `--ner_sft_save_steps`/`--ner_sft_eval_steps`/`--ner_grpo_eval_steps` lowered too, or `trainer.state.best_model_checkpoint` stays `None` and the post-training checkpoint push fails.

`run_full_pipeline.sh` explicitly whitelists every hyperparameter flag name as its own `--flag=value` bash `case` pattern, setting a same-named shell variable — keep that list (and the per-step invocations that consume those variables) in sync when adding/removing a hyperparameter, since an unrecognized flag is a hard error there rather than a silent passthrough.

`--ner_target_modules` selects between two LoRA target-module presets defined in `train_pipeline.py`'s `NER_TARGET_MODULES` dict: `"attention_only"` (`q/k/v/o_proj`) and `"all_linear"` (adds `gate/up/down_proj`).

## Module structure (`src/`)

- **`util_code.py`** — task-agnostic helpers shared across pipelines; nothing here carries the `ner`/`NER` marker, and nothing here should become task-specific — that belongs in the three files below. Currently just `load_adapter` (download a LoRA adapter from the HF Hub and attach it to a model via `peft.PeftModel.from_pretrained`), used by both `train_pipeline.py` (GRPO stage, to load the SFT adapter before continuing training) and `test_pipeline.py` (sft/grpo eval modes).
- **`dataset_code.py`** — turns the IOB-tagged Pile-NER dataset into the training format. Core transform is `format_ner_sft`: for each sample, detokenize the IOB tokens, extract entity→span-list dicts (`extract_ner_entity_spans`), sample a random subset of positive entity types (present in the sample) plus negative types (sampled by inverse frequency via `sample_ner_negatives`, weighted by `get_ner_entity_array_and_weights`), and build a 3-turn chat (system instructions + user text/entity-labels + assistant JSON) used as the SFT target. `create_ner_grpo_ds` reuses `create_ner_sft_ds` and just splits the last turn off into a separate `answer` column (GRPO needs `prompt` + `answer`, not a full target completion). `get_split_ner_ds` does a two-stage `train_test_split` to get train/validation/test. `compute_ner_negative_stats` reports positive/negative label balance for a formatted dataset — useful for sanity-checking data before an expensive training run.
- **`train_code.py`** — `execute_ner_sft` and `execute_ner_grpo` wrap `trl.SFTTrainer` / `trl.GRPOTrainer` with LoRA (`peft.LoraConfig`) and this repo's specific config (bf16, gradient checkpointing, wandb reporting, save/eval strategy). `ner_collate_fn` (SFT only) builds labels by masking everything before the `<start_of_turn>model` marker with `-100`, so only the assistant's JSON reply contributes to the loss. GRPO's `eos_token_id` is derived from the processor at call time (not hardcoded) so it stays correct if the base model changes — this pattern is repeated in `eval_code.py`'s `run_ner_batched_inference`; don't reintroduce a hardcoded EOS id.
- **`eval_code.py`** — inference + metrics + GRPO reward functions, the largest module.
  - Inference: `run_ner_batched_inference` applies the chat template, generates (greedy by default; pass `temperature`/`top_p` to switch to sampling), and returns cleaned responses plus a per-sample `truncated` flag (mirrors TRL's own `clipped_ratio` truncation definition). `clean_ner_prediction` strips markdown fences and chat-template turn markers from raw model output.
  - Metrics: two F1 modes, `"soft"` (token-set IoU, partial credit) and `"strict"` (exact match). `compute_ner_entity_counts` solves an optimal assignment (`scipy.optimize.linear_sum_assignment`) between GT and predicted spans per entity type in soft mode; strict mode short-circuits to a multiset intersection since exact-match scores are binary/transitive. `compute_ner_sample_counts` handles malformed JSON gracefully (returns a `json_error_flag` rather than raising) and matches entity-type keys case-insensitively (`lower_ner_keys`). `evaluate_ner_dataset` is the main entry point test_pipeline.py calls; it accumulates corpus-level (micro) F1 alongside per-sample-mean (macro) reward metrics, and optionally writes a completions parquet.
  - Reward functions (used by GRPO training, and also computed at test time for diagnostics via `compute_ner_sample_rewards`): two independent reward schemes selectable via `--ner_reward_fn`.
    - `"soft_f1"` (`ner_soft_f1_reward_fn`) — just the soft-F1 score per sample.
    - `"structured"` (default) — a level-based reward with early-exit gating: Level 1 rewards valid `Dict[str, List[str]]` JSON; Level 2 rewards correct entity-type keys (any wrong key or missing key caps the reward there); Level 3 scores extraction quality per entity type (exact-match precision/recall-style scoring via `_compute_ner_extraction_score`, clipped so a correctly-formatted-but-imperfect answer always beats malformed output). The four per-level reward functions (`ner_structured_format_reward_fn`, `ner_structured_key_matching_reward_fn`, `ner_structured_extraction_quality_positive_reward_fn`, `ner_structured_extraction_quality_negative_reward_fn`) are generated by the `_ner_structured_component_reward_fn` factory so TRL logs each component separately to wandb; `NER_REWARD_FUNCTIONS["structured"]` is the list GRPOTrainer actually receives, and their sum reproduces `compute_ner_structured_reward_components`'s combined value exactly. When changing reward logic, edit `compute_ner_structured_reward_components` (the shared implementation) — the factory-generated wrappers stay thin pass-throughs automatically.
- **`train_pipeline.py`** / **`test_pipeline.py`** — CLI entry points described above; each declares its own hyperparameter flags directly (see "Hyperparameter flags" above).

  > Note: these used to fail fast right after loading/merging the model if `generation_config.eos_token_id` didn't cover both the tokenizer EOS and `<end_of_turn>` — merging a LoRA adapter can silently drop it, which would otherwise let generation run to `max_new_tokens` instead of stopping at the turn boundary. That check (`eval_code.check_ner_eos_config`) was removed by explicit request; if truncated/runaway generations start showing up after an adapter-loading change, this is the first thing to suspect.

## Conventions worth knowing before editing

- Entity-type keys and span text are matched **case-insensitively** everywhere (`lower_ner_keys`, `.lower()` in extraction scoring) — this is deliberate, not an oversight; keep new comparison logic consistent with it unless there's a specific reason not to.
- `data/` is git-ignored (see `.gitignore`, which also whitelists a few legacy example subfolders — `grid_search/`, `test_baseline/`, `test_sft/` — that don't currently exist on disk and predate the current hyperparameter flags) — everything under `data/` (run outputs, caches) is local/ephemeral and won't be visible via git history.
- Model checkpoints are the source of truth on the HF Hub (`frc00/UniversalMedNER`), not in the local filesystem — don't assume a checkpoint referenced in a hyperparam file or script exists locally.
- Only top-level function/class/constant names, CLI flag names, and shell variable names carry the `ner`/`NER` marker — local variables, function parameters, and loop variables (e.g. `pile_ds`, `create_ds_fn`) do not. Naming pattern: verb-first names get `ner` inserted right after the verb (`evaluate_dataset` → `evaluate_ner_dataset`); everything else (single words, noun-phrase-first names, module constants) gets an `ner_`/`NER_` prefix (`tokenize` → `ner_tokenize`, `TARGET_MODULES` → `NER_TARGET_MODULES`). Reward-function/CLI *choice values* (`"structured"`, `"soft_f1"`, `"sft"`, `"grpo"`, etc.) are unaffected — only identifiers get the marker, not algorithm/mode names.
