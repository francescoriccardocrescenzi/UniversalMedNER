# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

UniversalMedNER fine-tunes MedGemma (`google/medgemma-1.5-4b-it`, an image-text-to-text model used here in text-only mode) for biomedical entity extraction. The pipeline has two stages: LoRA supervised fine-tuning (SFT) on synthetically-formatted data, then LoRA GRPO reinforcement learning on top of the SFT checkpoint, using custom reward functions. Training data comes from `disi-unibo-nlp/Pile-NER-biomed-IOB` (IOB-tagged NER, converted on the fly into instruction/JSON-output format) — the same source dataset is reused by both tasks below; only the prompt/target formulation differs.

There are two parallel tasks, selected via `--task {ner,lbl}`:
- **`ner`** (directed extraction) — the model is given the text plus a candidate list of entity types and must extract spans for each, including deliberately-included negative types it should return empty for.
- **`lbl`** (open-set labelling) — the model is given only the text, with no candidate list, and must both discover and type every entity itself.

Both tasks share one set of files (`dataset_code.py`, `train_code.py`, `eval_code.py`, `train_pipeline.py`, `test_pipeline.py`, `util_code.py`), each with its own shell driver (`run_full_pipeline.sh` for `ner`, `run_full_lbl_pipeline.sh` for `lbl`). Every identifier/flag/shell-variable that's genuinely task-specific carries an `ner_`/`NER_` or `lbl_`/`LBL_` marker; anything that turned out to work identically for both tasks was de-prefixed back to a plain name (e.g. `execute_sft`, `--random_seed`, `TARGET_MODULES`) — see "Hyperparameter flags" and "Module structure" below for exactly what's shared vs. split, and why. Truly task-agnostic code (nothing task-specific about it at all, not even by convention) lives in `util_code.py`.

## Setup

- A local venv already exists at `.venv` (Python 3.11, managed with `uv`). Activate with `source .venv/bin/activate`, or prefix commands with `.venv/bin/python`.
- Secrets live in a git-ignored `.env` file with `HF_TOKEN` (must belong to an account with MedGemma access) and `WANDB_API_KEY`. Scripts do `set -a; source .env; set +a`.
- `HF_HOME` is set to `data/.cache/huggingface` by the shell pipeline scripts so the HF cache lands inside the (git-ignored) `data/` directory rather than `~/.cache`.

## Running the pipeline

Everything runs from the repo root. Each run is identified by a `--label`, which maps to a `data/<label>/` directory that receives all outputs (metrics, checkpoints, completions) — it holds no input config. Hyperparameters are plain CLI flags (see "Hyperparameter flags" below), not a file; override any of them by passing `--flag=value` overrides to the relevant shell script (each recognized name is explicitly whitelisted there and forwarded individually to whichever steps use it — anything else is a hard error) or directly to the Python entry points.

`src/run_full_pipeline.sh --label=RUN_LABEL [-1] [-2] [-3] [-4] [-5] [--profile=standard|smoke] [--random_seed=42] [--ner_sft_learning_rate=2e-4] [--ner_grpo_beta=0.0] ...` (task `ner`) and `src/run_full_lbl_pipeline.sh` (same flags/mechanics, task `lbl`, `--lbl_*` hyperparameters) each run the same five stages end-to-end, or only the numbered steps passed:
1. Test the baseline (no adapter) model → `data/<label>/baseline_metrics.json`
2. SFT training → checkpoint pushed to HF Hub under `<label>_ner_sft` (or `<label>_lbl_sft`)
3. Test the SFT checkpoint → `data/<label>/sft_metrics.json`
4. GRPO training on top of the SFT checkpoint → checkpoint pushed under `<label>_ner_grpo` (or `<label>_lbl_grpo`)
5. Test the GRPO checkpoint → `data/<label>/grpo_metrics.json`

`--profile` (default `standard`) selects between two execution modes, identically in both scripts:
- `standard` — the behavior described everywhere else in this doc: hyperparameter shell variables default per the "Hyperparameter flags" section below and are overridable with `--flag=value`.
- `smoke` — ignores the `standard` defaults entirely and hardcodes its own fixed, non-overridable configuration in the shell script. All training/pipelines run on the VM (there is no local-GPU constraint), so smoke uses the real base model (`MODEL_REPO` is left at its default, `google/medgemma-1.5-4b-it`) and keeps every GPU-capacity knob (batch sizes, LoRA rank, `num_generations`, `max_completion_length`) at its `standard` value — it shrinks only data volume and run duration (`MAX_RAW_SAMPLES`, `*_MAX_VALIDATION_SAMPLES`, `*_MAX_TEST_SAMPLES`, `*_MAX_STEPS`/`*_SAVE_STEPS`/`*_EVAL_STEPS`, etc.) and disables wandb (`WANDB_MODE=disabled`), so the whole 5-step pipeline finishes in a few minutes while still exercising the real model at real capacity. **Any flag other than `--label`/`-N` is a hard error under `--profile=smoke`** — it's meant only to verify that new/modified code runs correctly before committing to a full run, always the same way, not to be tuned. Every value it sets is a plain existing (or newly added) hyperparameter flag under the hood — `smoke` is nothing but a fixed, different set of flag values, not a separate code path in the Python entry points. Checkpoints from a smoke run still get pushed to the HF Hub under `<label>_ner_sft`/`<label>_ner_grpo` (or the `lbl` equivalents) like any other run, so use a clearly-scoped `--label` (e.g. `smoke`).

Underlying Python entry points (also runnable directly, but every hyperparameter flag for the *selected* `--task` is required with no python-side default — see "Hyperparameter flags" below — so a standalone invocation must pass all of them explicitly; check `--help` for the full flag list):
- `src/train_pipeline.py --task {ner,lbl} --mode {sft,grpo} --save_folder ... --checkpoint_save_folder ... [--checkpoint_load_folder ...] [--ner_reward_fn|--lbl_reward_fn {structured,soft_f1}] --random_seed ... [...all hyperparameter flags for --task...]` — trains and, on completion, uploads the best checkpoint's LoRA adapter to the HF Hub repo `frc00/UniversalMedNER` (default `--checkpoint_repo`) under `path_in_repo=<checkpoint_save_folder>`.
- `src/test_pipeline.py --task {ner,lbl} --mode {baseline,sft,grpo} --metrics_path ... [--sft_checkpoint_folder ...] [--grpo_checkpoint_folder ...] [--temperature ...] [--top_p ...] [--verbose] --random_seed ... [...all hyperparameter flags for --task...]` — downloads the relevant adapter(s) from the Hub, evaluates on the `test` split, writes metrics JSON and a `completions.parquet` (prompt/prediction/ground-truth/reward per sample).

`--task` and `--mode` are **task-orthogonal control flags**: `--task` picks which dataset-prep logic runs (and which block of per-task hyperparameter flags is required), `--mode` picks which stage/checkpoint to run or evaluate, independent of task.

Checkpoints are **not** stored locally beyond transient training checkpoints — the SFT/GRPO adapters live on the HF Hub repo `frc00/UniversalMedNER`, keyed by the `--checkpoint_save_folder` / `--checkpoint_load_folder` names (by convention `<label>_ner_sft` / `<label>_ner_grpo`, or `<label>_lbl_sft` / `<label>_lbl_grpo`). `test_pipeline.py` and the GRPO stage of `train_pipeline.py` both `snapshot_download` the needed folder from that repo rather than reading local checkpoint dirs.

## Hyperparameter flags

There is no hyperparameter config file and no shared python module for hyperparameters — each shell script is the single source of truth for its task's defaults, as plain shell variables at the top of the script. Every hyperparameter is passed from the shell script to the Python entry points as its own individual `--flag value` argument (never bundled into an array, dict, JSON blob, or namespace object), and each Python entry point declares that flag as its own individual `argparse.add_argument(...)` call with `default=None` and no other python-side default — `train_pipeline.py`/`test_pipeline.py` use `args.<flag>` directly everywhere, with no intermediate config object.

Flags fall into three groups:
- **Pure path/identity plumbing** — unprefixed, shared verbatim by both tasks, not really "hyperparameters" at all: `--label`, `--model_repo`, `--checkpoint_repo`, `--checkpoint_save_folder`, `--checkpoint_load_folder`, `--save_folder`, `--metrics_path`, `--completions_path`, `--verbose`, `--temperature`, `--top_p`, `--sft_checkpoint_folder`, `--grpo_checkpoint_folder`, `--task`, `--mode`.
- **Genuinely shared hyperparameters** — same meaning and same default regardless of task, so they're a single unprefixed flag: `--dataset_repo`, `--random_seed`, `--validation_size`, `--test_size`, `--target_modules`, `--max_raw_samples`, and (test only) `--f1_mode`, `--skip_reward_metrics`.
- **Per-task hyperparameters** — carry an `ner_`/`NER_` or `lbl_`/`LBL_` marker because a single flag can't hold two independently-tunable defaults at once (e.g. `--ner_sft_learning_rate` / `--lbl_sft_learning_rate`, not a shared `--sft_learning_rate`). Grouped by stage:
  - NER-only (no `lbl_` counterpart — the candidate-list-sampling concept doesn't exist for labelling): `--ner_max_entities`, `--ner_max_negatives`.
  - sft (`train_pipeline.py` only): `--{ner,lbl}_sft_learning_rate --{ner,lbl}_sft_lora_rank --{ner,lbl}_sft_batch_size --{ner,lbl}_sft_gradient_accumulation_steps --{ner,lbl}_sft_num_epochs --{ner,lbl}_sft_max_train_samples --{ner,lbl}_sft_max_validation_samples --{ner,lbl}_sft_save_steps --{ner,lbl}_sft_eval_steps --{ner,lbl}_sft_max_steps`
  - grpo (`train_pipeline.py` always; `test_pipeline.py` only needs `--{ner,lbl}_grpo_max_completion_length`): `--{ner,lbl}_grpo_learning_rate --{ner,lbl}_grpo_lora_rank --{ner,lbl}_grpo_batch_size --{ner,lbl}_grpo_gradient_accumulation_steps --{ner,lbl}_grpo_num_generations --{ner,lbl}_grpo_max_completion_length --{ner,lbl}_grpo_num_epochs --{ner,lbl}_grpo_max_train_samples --{ner,lbl}_grpo_max_validation_samples --{ner,lbl}_grpo_beta --{ner,lbl}_grpo_temperature --{ner,lbl}_grpo_eval_steps --{ner,lbl}_grpo_max_steps`
  - test (`test_pipeline.py` only): `--{ner,lbl}_test_batch_size --{ner,lbl}_max_test_samples`
  - reward function selector: `--ner_reward_fn` / `--lbl_reward_fn`, both resolved against the one shared `eval_code.REWARD_FUNCTIONS` registry (see "Module structure" below).

Since only one task's flags are relevant per run, every per-task flag is declared with `default=None` (not `required=True`), and each entry point does **post-parse validation** via a `REQUIRED_BY_TASK = {"ner": [...], "lbl": [...]}` dict: `missing = [f"--{name}" for name in REQUIRED_BY_TASK[args.task] if getattr(args, name) is None]`, then `parser.error(...)` if anything's missing. This is the same pattern already used for `--sft_checkpoint_folder`/`--grpo_checkpoint_folder` being required only for `--mode in (sft, grpo)`/`grpo` respectively, just generalized to the task dimension. No shell script ever needs to invent values for the other task's flags.

`test_pipeline.py` always uses `--{ner,lbl}_grpo_max_completion_length` regardless of `--mode`, so generation length (and therefore truncation behavior) is comparable across baseline/SFT/GRPO testing, for whichever task is selected.

`--{ner,lbl}_*_max_train_samples`, `--{ner,lbl}_*_max_validation_samples`, `--{ner,lbl}_max_test_samples`, `--ner_max_negatives`, and `--max_raw_samples` are the only hyperparameters that default to `-1` ("no limit"/"unset") instead of being required; `0` is a real, distinct value for all of them, e.g. `--ner_max_negatives=0` forces zero negative entities. There is no shared conversion layer: every function that actually consumes one of these values checks for `-1` directly at the point of use (`dataset_code.format_ner_sft`/`create_ner_sft_ds`'s `max_negatives`, `eval_code.evaluate_dataset`'s `max_samples`, `train_code.execute_sft`/`execute_grpo`'s `max_train_samples`/`max_validation_samples`, and the raw-dataset truncation inline in both entry points) — values flow from CLI flag to consuming function unmodified. `--max_raw_samples`, unlike the others, truncates the *raw* dataset immediately after `datasets.load_dataset`, before any formatting/splitting — the other `max_*_samples` flags truncate post-formatting splits, by which point the full dataset has already been mapped over (including, for NER, the entity-frequency pass in `dataset_code.get_ner_entity_array_and_weights`).

`--{ner,lbl}_sft_save_steps`/`--{ner,lbl}_sft_eval_steps`/`--{ner,lbl}_grpo_eval_steps` (checkpoint/eval cadence, in steps) and `--{ner,lbl}_sft_max_steps`/`--{ner,lbl}_grpo_max_steps` (hard cap on optimizer steps, `-1` = unused/disabled, TRL's own default, overrides `--{ner,lbl}_*_num_epochs` once reached) are required like the other core per-task hyperparameters. They matter together: `load_best_model_at_end=True` needs at least one eval+save to have actually happened, so a run using few enough samples/steps that the default cadence never fires needs the save/eval-step flags lowered too, or `trainer.state.best_model_checkpoint` stays `None` and the post-training checkpoint push fails.

Each shell script explicitly whitelists every hyperparameter flag name (shared and its own task's per-task flags) as its own `--flag=value` bash `case` pattern, setting a same-named shell variable — keep that list (and the per-step invocations that consume those variables) in sync when adding/removing a hyperparameter, since an unrecognized flag is a hard error there rather than a silent passthrough.

`--target_modules` selects between two LoRA target-module presets defined in `train_pipeline.py`'s `TARGET_MODULES` dict: `"attention_only"` (`q/k/v/o_proj`) and `"all_linear"` (adds `gate/up/down_proj`) — a model-architecture choice, not a task-specific one, so it's shared.

## Module structure (`src/`)

- **`util_code.py`** — task-agnostic helpers shared across pipelines; nothing here carries a task marker, and nothing here should become task-specific — that belongs in the files below. Currently just `load_adapter` (download a LoRA adapter from the HF Hub and attach it to a model via `peft.PeftModel.from_pretrained`), used by both `train_pipeline.py` (GRPO stage, to load the SFT adapter before continuing training) and `test_pipeline.py` (sft/grpo eval modes).
- **`dataset_code.py`** — turns the IOB-tagged Pile-NER dataset into the training format for both tasks. Shared helpers: `extract_entity_spans` parses IOB `B-`/`I-` tags into an entity→span-list dict (used by both tasks' formatters); `get_split_ds` does a two-stage `train_test_split` to get train/validation/test; `to_grpo_ds` splits an SFT-formatted dataset's last (assistant) turn into a separate `answer` column (GRPO needs `prompt` + `answer`, not a full target completion) — purely structural, no task logic; `compute_negative_stats` reports positive/negative label balance for a formatted dataset (for `lbl` it degenerately reports 0% negative by construction, since there's no candidate list to sample negatives from — still a harmless sanity check).
  - NER (`format_ner_sft`): for each sample, detokenize the IOB tokens, extract entity→span-list dicts, sample a random subset of positive entity types (present in the sample) plus negative types (sampled by inverse frequency via `sample_ner_negatives`, weighted by `get_ner_entity_array_and_weights`), and build a 3-turn chat (system instructions + user text/entity-labels + assistant JSON) used as the SFT target. `create_ner_sft_ds` applies this over a whole dataset; `create_ner_grpo_ds` is `create_ner_sft_ds` piped through `to_grpo_ds`.
  - Labelling (`format_lbl_sft`): simpler — no candidate list to sample from, so it just takes *every* entity type present in the sample (no positive/negative sampling, no `max_entities` concept). The prompt drops the "entity labels" section entirely (nothing to show), asks the model to both find and type every entity itself, and its assistant target is `{entity.upper(): spans, ...}` for everything `extract_entity_spans` found. `create_lbl_sft_ds` applies this over a whole dataset; `create_lbl_grpo_ds` is `create_lbl_sft_ds` piped through `to_grpo_ds`.
- **`train_code.py`** — `execute_sft` and `execute_grpo` wrap `trl.SFTTrainer` / `trl.GRPOTrainer` with LoRA (`peft.LoraConfig`) and this repo's specific config (bf16, gradient checkpointing, wandb reporting, save/eval strategy); both are fully task-agnostic (no task-specific logic in either), called identically by both tasks' entry-point code with different argument values. `execute_grpo` takes an already-resolved `reward_funcs` list (e.g. `eval_code.REWARD_FUNCTIONS[args.ner_reward_fn]` or `[args.lbl_reward_fn]`) from its caller rather than looking one up itself, so it never needs to know which task's reward registry to consult. `collate_fn` (SFT only) builds labels by masking everything before the `<start_of_turn>model` marker with `-100`, so only the assistant's JSON reply contributes to the loss. GRPO's `eos_token_id` is derived from the processor at call time (not hardcoded) so it stays correct if the base model changes — this pattern is repeated in `eval_code.py`'s `run_batched_inference`; don't reintroduce a hardcoded EOS id.
- **`eval_code.py`** — inference + metrics + GRPO reward functions, the largest module, and **fully task-agnostic**: every function here operates purely on the shared `Dict[str, List[str]]` (entity type → spans) JSON schema, never on knowing entity types in advance, so nothing in this file carries a task marker and both tasks call it identically. This works because entity-type names are matched exactly (case-insensitive) against ground truth for both tasks — `lbl`'s model just has to learn the dataset's implicit type vocabulary from SFT examples rather than being shown it, but once it emits a prediction, scoring it is identical to NER.
  - Inference: `run_batched_inference` applies the chat template, generates (greedy by default; pass `temperature`/`top_p` to switch to sampling), and returns cleaned responses plus a per-sample `truncated` flag (mirrors TRL's own `clipped_ratio` truncation definition). `clean_prediction` strips markdown fences and chat-template turn markers from raw model output.
  - Metrics: two F1 modes, `"soft"` (token-set IoU, partial credit) and `"strict"` (exact match). `compute_entity_counts` solves an optimal assignment (`scipy.optimize.linear_sum_assignment`) between GT and predicted spans per entity type in soft mode; strict mode short-circuits to a multiset intersection since exact-match scores are binary/transitive. `compute_sample_counts` handles malformed JSON gracefully (returns a `json_error_flag` rather than raising) and matches entity-type keys case-insensitively (`lower_keys`). `evaluate_dataset` is the main entry point `test_pipeline.py` calls; it accumulates corpus-level (micro) F1 alongside per-sample-mean (macro) reward metrics, and optionally writes a completions parquet.
  - Reward functions (used by GRPO training, and also computed at test time for diagnostics via `compute_sample_rewards`): two independent reward schemes, shared by both tasks, selectable via `--ner_reward_fn`/`--lbl_reward_fn`.
    - `"soft_f1"` (`soft_f1_reward_fn`) — just the soft-F1 score per sample.
    - `"structured"` (default) — a level-based reward with early-exit gating: Level 1 rewards valid `Dict[str, List[str]]` JSON; Level 2 rewards correct entity-type keys (any wrong key or missing key caps the reward there — for `lbl` this means an invented type name that doesn't exactly match ground truth zeroes out at this level, same as a wrong NER key would); Level 3 scores extraction quality per entity type (exact-match precision/recall-style scoring via `_compute_extraction_score`, clipped so a correctly-formatted-but-imperfect answer always beats malformed output). The four per-level reward functions (`structured_format_reward_fn`, `structured_key_matching_reward_fn`, `structured_extraction_quality_positive_reward_fn`, `structured_extraction_quality_negative_reward_fn`) are generated by the `_structured_component_reward_fn` factory so TRL logs each component separately to wandb; `REWARD_FUNCTIONS["structured"]` is the list GRPOTrainer actually receives, and their sum reproduces `compute_structured_reward_components`'s combined value exactly. When changing reward logic, edit `compute_structured_reward_components` (the shared implementation) — the factory-generated wrappers stay thin pass-throughs automatically.
- **`train_pipeline.py`** / **`test_pipeline.py`** — CLI entry points described above; each declares `--task`/`--mode` plus its hyperparameter flags directly (see "Hyperparameter flags" above), dispatches to `create_{ner,lbl}_sft_ds`/`create_{ner,lbl}_grpo_ds` and the matching per-task argument values based on `args.task`, and resolves `reward_funcs = ec.REWARD_FUNCTIONS[args.ner_reward_fn if args.task == "ner" else args.lbl_reward_fn]` before calling `execute_grpo`. Everything else (model loading, `execute_sft`/`execute_grpo`, `evaluate_dataset`) is identical code for both tasks — only the argument *values* branch on `args.task`, not the functions called. wandb run naming is `f"{args.label}_{args.task}_{args.mode}"`.

  > Note: `train_pipeline.py` used to fail fast right after loading/merging the model if `generation_config.eos_token_id` didn't cover both the tokenizer EOS and `<end_of_turn>` — merging a LoRA adapter can silently drop it, which would otherwise let generation run to `max_new_tokens` instead of stopping at the turn boundary. That check (`eval_code.check_ner_eos_config`) was removed by explicit request; if truncated/runaway generations start showing up after an adapter-loading change, this is the first thing to suspect.

## Conventions worth knowing before editing

- Entity-type keys and span text are matched **case-insensitively** everywhere (`lower_keys`, `.lower()` in extraction scoring) — this is deliberate, not an oversight; keep new comparison logic consistent with it unless there's a specific reason not to.
- `data/` is git-ignored (see `.gitignore`, which also whitelists a few legacy example subfolders — `grid_search/`, `test_baseline/`, `test_sft/` — that don't currently exist on disk and predate the current hyperparameter flags) — everything under `data/` (run outputs, caches) is local/ephemeral and won't be visible via git history.
- Model checkpoints are the source of truth on the HF Hub (`frc00/UniversalMedNER`), not in the local filesystem — don't assume a checkpoint referenced in a hyperparam file or script exists locally.
- Naming convention: only top-level function/class/constant names, CLI flag names, and shell variable names carry a task marker — local variables, function parameters, and loop variables (e.g. `pile_ds`, `create_ds_fn`) do not. A name gets an `ner_`/`NER_` or `lbl_`/`LBL_` marker only if the thing it names is genuinely task-specific (different logic or a different independently-tunable default per task); anything that behaves identically for both tasks is left unprefixed, even if it's currently only exercised by one caller. Verb-first names get the marker inserted right after the verb (`evaluate_dataset` stayed unprefixed since it's shared; `format_ner_sft`/`format_lbl_sft` are split because the two format differently); everything else (single words, noun-phrase-first names, module constants) gets a prefix (`TARGET_MODULES` is shared; `NER_MAX_ENTITIES`/`LBL_...` would be split if labelling ever needed an equivalent). Reward-function/CLI *choice values* (`"structured"`, `"soft_f1"`, `"sft"`, `"grpo"`, `"ner"`, `"lbl"`, etc.) are unaffected — only identifiers get the marker, not algorithm/mode/task names.
